# Healix Bug-Bash — Prompt 2: Live Partial Ingest + In-Flight Dashboard

---

## 1. Problem Statement

### Context

Healix is an AI-powered QA-replacement MCP (Model Context Protocol) tool. It runs a multi-tier Playwright test pipeline against a target application and reports results to a Next.js dashboard. The pipeline involves:

- Auto-detecting project settings
- Launching the target app
- Generating Playwright tests via AI (calls to GPT-5.5-mini)
- Executing tests across three tiers (public, authenticated, API)
- Triaging failures with AI
- Uploading artifacts to Supabase Storage
- POSTing a final report to `/api/test-runs/ingest`

### The Problem

**A Healix run is a 25-minute black box.**

Today's architecture has a critical design flaw: **the dashboard only receives data at the very end of the pipeline**, in a single large POST to `/api/test-runs/ingest`. This means:

1. **Nothing shows up for 25 minutes** — users have no feedback during the run
2. **If the worker crashes, every finding dies with it** — there is zero persistence of intermediate state
3. **There is no way to tell if the run is alive or stalled** — a crashed worker looks identical to a slow-running one
4. **No tier-level visibility** — users can't see which tiers (A/B/C) are passing or failing in real time

The hackathon specification states the target:

> *"A QA-replacement tool needs to show value at the 90-second mark, not the 25-minute mark."*

**Done-when criteria:**
- Tier-0 findings appear at the 90-second mark without refresh
- Kill worker mid-run → dashboard flips to `stalled` within 5 minutes
- Partial findings preserved after worker kill
- Dashboard shows `completed-partial` (not `error_reported`) when run dies mid-way

## 2. Root Cause Analysis

### Why is everything delayed until the end?

Tracing the pipeline code reveals the exact bottleneck:

```
runPipeline()
  ├── Port pre-flight
  ├── App startup
  ├── Test generation (AI — can take 10–15 min)
  ├── Credential injection
  ├── playwright.runTests()  ← all tiers run here in parallel
  ├── AI failure triage
  └── reportGen.generate()
        └── POST /api/test-runs/ingest  ← ← ← ONLY point of data transfer
```

There is exactly **one call to the webapp** (`ingestTestRun`) and it happens at the very end. The entire `testRuns` row is created in this single call — there is no row in the database while the pipeline is running.

The only "live" mechanism that existed before this work was:
- `POST /api/test-runs/phase` — writes to `mcpTelemetryEvents`, not `testRuns`
- A synthetic "live run" concept tracked in memory / a flat table

Neither mechanism persists findings. Both disappear if the run crashes.

### What is available early in the pipeline?

| Time (approx) | What exists |
|---------------|-------------|
| 0s | `runId` is known, `config` is loaded |
| 15–60s | App starts up |
| ~60–90s | Tier-0 deterministic QA contract specs are generated |
| 10–20 min | AI generation completes |
| +5 min | Playwright execution completes |
| +2 min | AI triage completes |
| End | Report ingested to dashboard |

**Key insight:** Tier-0 findings exist at the 90-second mark. They are generated by a deterministic algorithm (not AI), making them the ideal first partial signal.

## 3. Approach

### Design Philosophy

The solution follows three principles:

1. **Non-blocking everywhere** — every new call to the webapp is fire-and-forget. If the webapp is unreachable, the pipeline continues without any interruption.
2. **Extend, don't replace** — the existing `ingestTestRun` flow is left intact. Partial ingest supplements it; the final ingest remains the source of truth for complete runs.
3. **Persist early, display live** — write partial state to the database row, then use Supabase realtime to push that state to the browser without polling.

### Architecture

```
Pipeline Worker (MCP)                     Webapp (Next.js + Supabase)
─────────────────────                     ──────────────────────────
Run starts
  │
  ├─► POST /api/test-runs/create ─────►  INSERT test_runs (status=running)
  │                                              │
  │   [every 30s]                                │
  ├─► PATCH /api/test-runs/:id/heartbeat ──►  UPDATE last_heartbeat_at
  │                                              │
  │   [~90s: Tier-0 ready]                       │
  ├─► PATCH /api/test-runs/:id/findings  ──►  UPDATE partial_findings (append)
  │                                              │
  │   [execution complete]                        │
  ├─► PATCH /api/test-runs/:id/findings  ──►  UPDATE tier_results
  │                                              │
  │   [pre-report]                               │
  ├─► PATCH /api/test-runs/:id/complete  ──►  UPDATE status=completed_partial
  │                                              │
  └─► POST /api/test-runs/ingest  ────────►  Final authoritative ingest
                                                 │
                                      Supabase Postgres Realtime
                                                 │
                                         Browser (React)
                                      ← push every UPDATE event
                                      → setTestRun(update)
                                      → TierPillBanner re-renders
                                      → "stalled" flip if heartbeat > 5min
```

### Stalled Detection (Two-Layer)

**Layer 1 — Server-side (GET):** The `GET /api/test-runs/:id` route checks `lastHeartbeatAt` on every request. If the run's status is `running` and the heartbeat is older than 5 minutes, it returns `status: 'stalled'` in the response.

**Layer 2 — Client-side (interval):** The React page runs a 15-second interval. If `status === 'running'` and `lastHeartbeat > 5 min ago`, it flips the local state to `stalled` immediately — no server round-trip needed.

## 4. Step-by-Step Flow

This is exactly what happens from the moment a developer runs Healix to the moment results are fully visible on the dashboard.

---

### Phase 1 — Pipeline Starts (T = 0s)

```
Developer runs: healix_test_my_app
```

1. `runPipeline()` begins in `pipeline-worker.js`
2. `runId` is generated (a UUID for this specific run)
3. `durableClient` is created using `HEALIX_API_KEY`
4. **[NEW]** `durableClient.createRun()` fires → `POST /api/test-runs/create`
   - A `test_runs` row is inserted in the database with `status = 'running'`
   - `last_heartbeat_at` is set to now
5. The dashboard page for this run is now accessible — shows **"In Progress"** badge

> **Before this change:** No database row existed during the run. Opening the dashboard showed a 404 or blank page.

---

### Phase 2 — App Startup + Context Gathering (T = 0–60s)

1. Port pre-flight check runs
2. Target app is started via `multi-service-starter.js`
3. Browser exploration runs (Playwright heuristic or Python browser-use)
4. Codebase context is gathered — routes, forms, API endpoints, QA contracts
5. **[NEW]** Heartbeat timer starts: every 30 seconds, `PATCH /api/test-runs/:id/heartbeat` fires silently
   - `last_heartbeat_at` is refreshed in the DB
   - Dashboard knows the run is alive

> **Before this change:** No heartbeats. A crashed worker and a slow worker were indistinguishable.

---

### Phase 3 — Tier-0 Deterministic Generation (T ≈ 60–90s)

1. `ensureQaContractSpec()` runs — generates deterministic QA contract specs from source code analysis (no AI)
2. Specs are written to `tests/generated/` (e.g. `qa-contracts.spec.ts`)
3. **[NEW]** `durableClient.patchFindings()` fires → `PATCH /api/test-runs/:id/findings`
   - Tier-0 findings appended to `partial_findings` JSONB column
   - `current_phase` set to `tier0_complete`
4. **Supabase realtime broadcasts the UPDATE** to any browser subscribed to this run
5. Dashboard **tier-pill banner updates live** — Tier-0 contracts visible without refresh

> **Before this change:** Nothing was visible at 90 seconds. Users waited the full 25 minutes.

---

### Phase 4 — AI Test Generation (T ≈ 2–15 min)

1. `generateWithFallbackChain()` is called — sends codebase context to `POST /api/generate-tests`
2. GPT generates Playwright specs for all three tiers (sync or Inngest async)
3. Generated specs are validated and quality-audited
4. Heartbeat continues firing every 30s throughout — dashboard stays "In Progress"
5. If generation fails completely → pipeline throws, `patchComplete` fires with `status = 'error'`

---

### Phase 5 — Test Execution (T ≈ 15–20 min)

1. Credentials are injected per role into `.healix/` storage state files
2. `playwright.runTests()` runs all three tiers in parallel:
   - **Tier A** — Public flows (no auth)
   - **Tier B** — Per-role authenticated flows (one Playwright project per role)
   - **Tier C** — API/backend tests
3. Heartbeat fires every 30s throughout execution
4. When execution completes:
   - **[NEW]** `durableClient.patchFindings()` fires with final `tierResults`
   - Dashboard tier pills update: `Tier A · 12/15 ✓  Tier B · Admin 8/8 ✓  Tier C · 5/7 ✗`

---

### Phase 6 — AI Failure Triage + Pre-Report (T ≈ 20–22 min)

1. Failed tests are triaged: deterministic classifier runs first, then AI analysis
2. `computeTierResults()` produces final pass/fail counts per tier
3. **[NEW]** `durableClient.patchComplete()` fires → `PATCH /api/test-runs/:id/complete`
   - Preliminary status set (`passed` or `completed_partial`)
   - Final tier stats merged into the row
   - Dashboard badge updates to final status **before** the big ingest

---

### Phase 7 — Final Ingest (T ≈ 22–25 min)

1. `reportGen.generate()` calls `POST /api/test-runs/ingest` (the original single large call)
2. Full `report_json`, `ai_analysis`, screenshots, traces are written
3. This is the **authoritative final state** — overwrites preliminary status if different
4. `partial_findings` column is preserved (useful for debugging partial vs final diff)
5. Dashboard deep-link opens automatically

---

### What Happens If the Worker Dies Mid-Run

```
T = 8 min: Worker crashes (OOM, Ctrl+C, network cut, etc.)
             ↓
T = 8 min: Last heartbeat was at T = 7:30
             ↓
T = 13 min: First user opens the run page
           → GET /api/test-runs/:id
           → resolveEffectiveStatus() detects heartbeat age = 5m30s > 5min
           → returns status: 'stalled'
           → Dashboard shows orange "Stalled" badge + "Last seen 5 min ago"
             ↓
T = 13–28 min: Any user already on the page
           → Client-side 15s interval checks heartbeat age
           → Flips local status to 'stalled' without refresh
             ↓
Findings visible: Whatever patchFindings calls had already fired are
                  persisted in partial_findings — visible on page load
```

---

### Full Timeline Summary

| Time | Event | Dashboard shows |
|------|-------|-----------------|
| T = 0s | `createRun` POST fires | "In Progress" page accessible |
| T = 30s | First heartbeat | Run confirmed alive |
| T = 90s | Tier-0 specs generated, `patchFindings` fires | Tier-0 contracts appear live |
| T = 2–15 min | AI generation runs | Heartbeat keeps badge "In Progress" |
| T = ~20 min | Execution done, `patchFindings` tier results | Tier pills show pass/fail counts |
| T = ~22 min | `patchComplete` fires | Preliminary status badge updates |
| T = ~25 min | Final `ingest` POST | Full report, traces, AI analysis visible |
| **If crash at any point** | Heartbeat stops | "Stalled" badge within 5 min |

### Step 2 — New API Routes

#### `POST /api/test-runs/create`
**File:** `webapp/src/app/api/test-runs/create/route.ts`

Creates a `testRuns` row at the start of the pipeline with `status = 'running'`.

- Auth: `x-api-key` header (same as ingest)
- Body: `{ run_id, creation_name, project_path }`
- Idempotent: if a row already exists for `run_id + userId`, returns 200 without error
- Returns: `{ success: true, test_run_id, dashboard_url }`

```typescript
await db.insert(testRuns).values({
  id: run_id,
  userId,
  status: 'running',
  lastHeartbeatAt: now,
  ...
})
```

---

#### `PATCH /api/test-runs/:id/findings`
**File:** `webapp/src/app/api/test-runs/[id]/findings/route.ts`

Appends findings to `partialFindings` and optionally updates `tierResults`.

- Auth: `x-api-key`
- Body: `{ findings: [], tier_results?: {}, phase?: string }`
- Merge strategy: **append** (never overwrite) — safe to call multiple times
- Returns: `{ ok: true, finding_count }`

```typescript
const merged = [...existing, ...incomingFindings]
await db.update(testRuns).set({ partialFindings: merged, tierResults: normalizedTier, ... })
```

---

#### `PATCH /api/test-runs/:id/heartbeat`
**File:** `webapp/src/app/api/test-runs/[id]/heartbeat/route.ts`

Updates `lastHeartbeatAt` to now. Called every 30 seconds by the worker.

- Auth: `x-api-key`
- Body: `{ phase?: string }` (optional label for the current execution stage)
- Returns: `{ ok: true }`

---

#### `PATCH /api/test-runs/:id/complete`
**File:** `webapp/src/app/api/test-runs/[id]/complete/route.ts`

Sets the final status and optionally merges final stats into the row.

- Auth: `x-api-key`
- Body: `{ status: 'completed' | 'completed_partial' | 'error', final_data?: { report, tier_results, pipeline_error } }`
- Allowed statuses: `completed`, `completed_partial`, `error`, `passed`, `failed`
- Returns: `{ ok: true, status }`

---

#### Stalled Detection in `GET /api/test-runs/:id`
**File:** `webapp/src/app/api/test-runs/[id]/route.ts`

Added `resolveEffectiveStatus()` helper:

```typescript
const STALE_THRESHOLD_MS = 5 * 60 * 1000

function resolveEffectiveStatus(status, lastHeartbeatAt) {
  if (status !== 'running') return status
  if (!lastHeartbeatAt) return status
  const age = Date.now() - new Date(lastHeartbeatAt).getTime()
  return age > STALE_THRESHOLD_MS ? 'stalled' : status
}
```

Both response paths (live-run and regular) now include `partial_findings` and `last_heartbeat_at` in the response payload.

### Step 3 — MCP Client Methods

**File:** `testbot-mcp/src/webapp-client.js`

Added a `_patch()` HTTP helper (mirrors `_post()` but uses `PATCH`, no retry loop, 8s ceiling) and four new public methods:

```javascript
// Create the run row immediately at pipeline start
async createRun({ runId, creationName, projectPath })

// Append findings + optional tier counts to the partial ingest column
async patchFindings(runId, { findings, tierResults, phase })

// Touch last_heartbeat_at — called every 30s, completely silent on failure
async patchHeartbeat(runId, phase)

// Set the final run status before/after the big ingest call
async patchComplete(runId, status, finalData)
```

All four methods are **fire-and-forget** — they `catch(() => null)` at the call site and log a warning without propagating errors. The pipeline is never blocked by these calls.

### Step 4 — Pipeline Worker Wiring

**File:** `testbot-mcp/src/pipeline-worker.js`

Four insertion points, all wrapped in `durableClient && ...` guards so the pipeline degrades gracefully when no API key is configured:

#### 4a. Pipeline start — create run row
```javascript
// After durableClient is initialized (~line 8630)
if (durableClient) {
  durableClient.createRun({
    runId,
    creationName: config.projectName || 'Unnamed run',
    projectPath: config.projectPath,
  }).catch(() => undefined);
}
```

#### 4b. After Tier-0 generation (~90s mark)
```javascript
// After deterministicTier0Pack.written check, inside generateWithFallbackChain
if (durableClient && deterministicTier0Pack?.written) {
  const tier0Findings = Object.entries(deterministicTier0Pack.qaContractQuestions || {})
    .map(([endpoint, questions]) => ({
      source: 'tier0_deterministic',
      endpoint,
      tests: Array.isArray(questions) ? questions.length : 0,
    }));
  durableClient.patchFindings(runId, {
    findings: tier0Findings,
    phase: 'tier0_complete',
  }).catch(() => undefined);
}
```

> **Important:** `durableClient` is defined in `runPipeline()` but the Tier-0 code lives inside `generateWithFallbackChain()` — a separate function. It must be passed as a parameter:
> ```javascript
> // Function signature
> async function generateWithFallbackChain({ ..., durableClient = null })
> // Call site in runPipeline
> await generateWithFallbackChain({ ..., durableClient })
> ```
> Without this, the pipeline crashes with `ReferenceError: durableClient is not defined` before generating any specs.

#### 4c. Heartbeat loop during execution
```javascript
// Before playwright.runTests()
let _heartbeatTimer = null;
if (durableClient) {
  _heartbeatTimer = setInterval(() => {
    durableClient.patchHeartbeat(runId, 'executing').catch(() => undefined);
  }, 30_000);
}
try {
  testResults = await withStageBudget(runBudget, 'execution', ...);
} finally {
  if (_heartbeatTimer) { clearInterval(_heartbeatTimer); _heartbeatTimer = null; }
}
```

#### 4d. After tierResults computed + pre-report
```javascript
// After computeTierResults()
if (durableClient && tierResults) {
  durableClient.patchFindings(runId, { tierResults, phase: 'execution_complete' }).catch(() => undefined);
}

// Before reportGen.generate()
if (durableClient) {
  const prelim = testResults?.failed === 0 && testResults?.total > 0 ? 'passed' : 'completed_partial';
  durableClient.patchComplete(runId, prelim, { report: { stats: finalStats }, tier_results: tierResults })
    .catch(() => undefined);
}
```

### Step 5 — Supabase Realtime Helper

**File:** `webapp/src/lib/supabase/realtime.ts`

```typescript
export function subscribeToRun(
  runId: string,
  onUpdate: (update: RunRealtimeUpdate) => void
): () => void {
  const supabase = createSupabaseBrowserClient()
  const channel = supabase
    .channel(`run-${runId}`)
    .on('postgres_changes', {
      event: 'UPDATE',
      schema: 'public',
      table: 'test_runs',
      filter: `id=eq.${runId}`,
    }, (payload) => {
      const row = payload.new
      onUpdate({
        status:           row.status,
        tier_results:     row.tier_results,
        partial_findings: row.partial_findings,
        last_heartbeat_at: row.last_heartbeat_at,
        current_phase:    row.current_phase,
        total_tests:      row.total_tests,
        passed_tests:     row.passed_tests,
        failed_tests:     row.failed_tests,
        skipped_tests:    row.skipped_tests,
        updated_at:       row.updated_at,
      })
    })
    .subscribe()
  return () => supabase.removeChannel(channel)
}
```

> **Manual step required:** Enable realtime on the `test_runs` table in Supabase Dashboard → Database → Replication → add `test_runs` to `supabase_realtime` publication.

## 7. Key Design Decisions

| Decision | Rationale |
|----------|-----------|
| Fire-and-forget for all new MCP calls | Pipeline reliability is non-negotiable. A slow webapp cannot stall a 20-minute test run. |
| Append-only `partialFindings` | Prevents race conditions when multiple PATCH calls arrive out of order. Findings accumulate; none are lost. |
| Keep final `ingestTestRun` call intact | The full ingest is the source of truth. Partial ingest is additive — it doesn't replace anything. |
| Client-side stalled detection (15s interval) | Avoids a server-side cron job. The client already knows `lastHeartbeat`; no extra infra needed. |

## 9. Post-Implementation Bug Fixes

### Fix 1 — `durableClient is not defined` (pipeline crash)

**Symptom:** `Backend test generation failed: durableClient is not defined` — the run crashed before generating any specs.

**Root cause:** The Tier-0 `patchFindings` code was placed inside `generateWithFallbackChain()` (defined at line ~7246), but `durableClient` is only defined inside `runPipeline()` (line ~8647) — a completely separate function. JavaScript `const` does not cross function boundaries.

**Fix:** Added `durableClient = null` to `generateWithFallbackChain`'s parameter destructuring and passed it through at the call site in `runPipeline`:

```javascript
// Function signature (pipeline-worker.js ~line 7246)
async function generateWithFallbackChain({
  ..., durableClient = null   // ← added
})

// Call site in runPipeline (~line 9355)
await generateWithFallbackChain({
  ..., durableClient          // ← passed through
})
```

### Fix 2 — React hydration error (browser extension attributes)

**Symptom:** Console error: `A tree hydrated but some attributes of the server rendered HTML didn't match the client properties` — attributes like `data-liner-extension-version="7.18.14"` and `data-be-installed="true"` were being injected into `<html>` and `<body>` by browser extensions before React hydrated.

**Fix:** Added `suppressHydrationWarning` to both tags in `webapp/src/app/layout.tsx`:

```tsx
<html lang="en" suppressHydrationWarning>
  <body ... suppressHydrationWarning>
```

This only suppresses mismatches on the root tags themselves — not on any app content inside them. It is the [official Next.js recommendation](https://nextjs.org/docs/messages/react-hydration-error) for extension-injected attributes.
